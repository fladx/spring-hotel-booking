# Architecture Decision Records

## ADR-001 — локальные транзакции и компенсируемая сага
PENDING фиксируется в Booking DB перед сетевым вызовом. Распределённой транзакции нет.
При неуспехе CANCELLED и компенсация отражаются отдельно: отменённая бронь не является доказательством
освобождённого номера. Pending compensation видна клиенту и повторяется ограниченно.
Если авторизационный JWT истёк, автоматическая попытка прекращается; владелец повторяет DELETE с новым JWT.
Токен не сохраняется в БД и логах. Ограничение учебного варианта явно показано в API/документации.

## ADR-002 — защита от поздней доставки
Идемпотентный release для неизвестного owner/requestId создаёт tombstone. Иначе сетевой тайм-аут
может привести к ситуации release→late reserve→утечка брони. Tombstone хранится в том же ledger,
что и резервации, и не удаляется автоматически. RequestId никогда не переиспользуется для новой брони.

## ADR-003 — конкурентный выбор
Hotel держит pessimistic lock единственной служебной строки, выполняя подбор, проверку пересечения
и создание резервации одной локальной транзакцией. Решение простое и проверяемое для учебного стенда.
Цена — сериализация конкурентных выделений. При росте нагрузки: отдельные lock-полосы на hotelId,
постоянная БД и задокументированный порядок получения блокировок.

## ADR-004 — API и безопасность
Примерные URI задания нормализованы до /api/* без скрытого rewrite. Внутренние команды вынесены
в /internal/* и не маршрутизируются Gateway. Localhost по умолчанию ограничивает прямой доступ;
в реальном развёртывании дополнительно нужны network policy и отдельная identity сервиса.
Каждый бизнес-сервис сам проверяет JWT. HMAC выбран для понятного учебного запуска; ключ из конфигурации
демонстрационный и публичный, использовать его вне изолированного стенда нельзя.

## ADR-005 — временная модель и равномерная загрузка
Период [start,end), LocalDate, минимум одна ночь. timesBooked — историческое число успешных
выделений, не текущая загрузка. Отмена не уменьшает его. autoSelect игнорирует roomId и выбирает
минимальный timesBooked, затем минимальный id. Это обеспечивает предсказуемые tie-breaks.

## ADR-006 — учебный жизненный цикл H2
Каждый бизнес-сервис использует отдельную H2 in-memory БД, как требуется заданием.
Перезапуск только Hotel обнулит его ledger при сохранении работающего Booking; это не сценарий
гарантированной отказоустойчивости. Для повторяемой демонстрации перезапускайте весь стенд целиком.
Для сохранения согласованности через рестарты нужны постоянные БД обоих сервисов и recovery/outbox.
