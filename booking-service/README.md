# Booking service
Java 17 / Spring Boot. Start with Eureka, or `EUREKA_ENABLED=false`. `DEMO_USERS=true` explicitly enables public local fixtures: admin/admin-demo-123 and demo/user-demo-123. Never enable in production. Registration always assigns USER. JWT lasts one hour; role changes/deletions do not revoke existing tokens (deploy a revocation policy in production).

POST /api/auth/register and /login: `{ "username":"alice", "password":"password123" }`. JWT response `accessToken`. Admin CRUD /api/users uses username/password/role. Booking CRUD: POST, GET collection/id, DELETE id. Collection paging `page=0&size=20`, max100. POST payload `{ "requestId":"unique-client-key", "roomId":1, "autoSelect":false, "startDate":"2027-01-01", "endDate":"2027-01-03" }`; auto-select optionally supplies hotelId (omit to search all hotels) and ignores roomId, even a negative roomId. Dates are half-open [start,end), maximum365 nights. Same user/key/payload returns same booking; payload mismatch409. Lists and individual reads/cancellation only access caller-owned rows, even for admins.

Saga: local PENDING commit -> remote reserve -> local CONFIRMED commit. Reservation business conflicts return409; dependency timeout/5xx/open-circuit failures return503. Any uncertain reservation failure locally CANCELLED with persisted compensation before remote release. Release tombstones prevent late allocation. Application startup compensates stranded PENDING rows. Unique owner/requestId constraint protects duplicate creation. A bounded set of 256 reentrant lock stripes, keyed by owner/requestId, serializes each local booking saga including its HTTP calls. Different stripes proceed concurrently; hash collisions may serialize unrelated bookings. Cancellation of the same booking waits for its active reservation call. Retry and startup recovery re-read state after acquiring the stripe, so stale snapshots cannot retry completed cleanup or cancel an already confirmed booking. These locks coordinate only one service instance; production should use per-booking ownership/leases. Remote calls use1500ms connect/read timeout; reservation retries at most2 attempts with50ms delay only for transport/5xx errors. A Resilience4j circuit opens10s when >=50% of its6-call window fail after at least3 calls; business4xx do not count as failures. Release bypasses the reservation circuit so cleanup stays possible. Durable pending release retries max8 attempts, increasing delay capped60s. The original identity JWT is retained only in a bounded in-memory map until token expiry or release success, never persisted or logged. If expired/exhausted, owner repeats DELETE with fresh JWT to reset retry budget. Pending state/attempt counts and ownerRetryRequired appear in booking API; alert operators on exhausted pending releases. Production should restrict DB access, configure persistent BOOKING_DB_URL, migrations and backups. Default in-memory H2 is tutorial-only and loses all state on process exit; file H2 preserves pending compensation across restart, but owner must DELETE again with a fresh token to authorize release. Automatic startup recovery assumes a single booking-service instance; multi-instance production requires leases/outbox worker locking. No HTTP request is executed in a local DB transaction. A short cache-admission monitor, never held during HTTP, preserves the 10,000-credential hard limit across booking stripes.

Local OpenAPI: http://localhost:8081/v3/api-docs and Swagger UI: http://localhost:8081/swagger-ui/index.html. Server binds loopback by default; set SERVER_ADDRESS explicitly for container networking. Local user_id foreign key prevents deleting accounts with booking history; password hashes never appear in user DTOs. Remote room IDs intentionally have no cross-service FK.

Confirmation/cancellation transitions lock the local booking row and only PENDING may become CONFIRMED. A concurrent cancellation cannot be revived by a late reserve response; compensation runs outside that local transaction. Integration tests use real HTTP stub plus H2, checking committed PENDING visibility, cancellation races, lost/late responses, release tombstones, owner JWT recovery, idempotency/concurrency, bounded retries and circuit behavior.

Concurrency regression tests additionally use real H2 with a controlled Hotel client to verify independent booking progress, duplicate requests, stale retry/recovery snapshots, owner-authenticated retry races, retry exhaustion, and the credential-cache limit.
